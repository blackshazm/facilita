# Phase Context — 5.2: Anti-fraud & Tiering Engine
**Date**: 2026-05-03

## Domain
The core domain for this phase is **Trust & Operational Scaling**. We are implementing the automated safeguards (Anti-fraud) and incentive structures (Tiers) that allow FACILITA to grow without proportional increases in manual backoffice overhead.

## Locked Requirements (from SPEC.md)
- [ ] **Strict Geofencing**: Mandatory 500m check-in validation.
- [ ] **Velocity Check**: Limit of 20 services/day before blocking payouts.
- [ ] **Tier System**: Bronze (D+15, 22%), Prata (D+7, 20%), Ouro (D+2, 18%).
- [ ] **Daily Recalculation**: Tiers updated once every 24h.
- [ ] **Backoffice MVP**: Dashboard at `/admin` for fraud and tier management.

## Implementation Decisions

### 1. Backend Security & Validation
- **Check-in Logic**: The Backend MUST verify coordinates using PostGIS `ST_Distance`. If the distance to the order address exceeds 500m, the API must return a `403 Forbidden` error.
- **RBAC**: The `Identity` module's `UserRole` enum will be extended with `ADMIN`. Administrative routes in the PWA and API will be protected by a `RolesGuard` checking for this role.

### 2. Fraud Detection Architecture
- **Event-Driven**: The `Fraud` module will listen for `order.completed` events via `EventEmitter2`.
- **Async Processing**: Velocity checks will be performed asynchronously. If a violation is detected, the `Fraud` module will emit a `fraud.detected` event or directly call the `Payments` service to flag the specific Payout as `SUSPICIOUS`.

### 3. Tier Management & Jobs
- **BullMQ Integration**: The daily tier recalculation will be implemented as a `Repeatable Job` in BullMQ, scheduled for 00:00 server time.
- **Persistence**: Lifetime metrics (order count, average rating) used for tiering will be aggregated from the `Orders` and `Reviews` modules.

### 4. Backoffice Implementation
- **Module Structure**: The dashboard will be built as a protected directory `/src/app/admin` within the existing Next.js Client App (PWA) to leverage the existing design system (Emerald 2.0).

## Code Context & Patterns
- **Geo Queries**: Reference `apps/api/src/modules/matching/adapters/postgis-matching.adapter.ts` for PostGIS query patterns.
- **Events**: Use the established `EventEmitter2` patterns found in `apps/api/src/modules/payments/application/authorize-payment.usecase.ts`.
- **Financial Precision**: Maintain `BigInt` for all wallet-related calculations as established in Phase 5.1.
