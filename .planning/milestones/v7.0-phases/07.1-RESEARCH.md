# Phase 7.1: Payout Automation & Ledger Hardening — Research

**Date:** 2026-05-06
**Status:** COMPLETE

## 1. Gateway Integration: Pagar.me V5
The project currently uses Pagar.me V5 for payments. For payouts, we must use the **Recipients API**.

### Key Endpoints:
- `POST /recipients`: Create a recipient for each provider.
- `GET /recipients/{id}/balance`: Check available balance in the gateway.
- `POST /transfers`: Create a transfer (payout) to the recipient's bank account.

### Bank Data Requirements:
- Bank Code (COMPE)
- Branch Number + Check Digit
- Account Number + Check Digit
- Account Type (checking, savings, etc.)
- Holder Name + Document (must match our KYC).

## 2. BullMQ Payout Scheduler
We already use BullMQ for `release-payout` jobs in `payouts` queue.

### Proposed Architecture:
1.  **Payout Processor**: The existing `payouts` queue processor will be extended.
2.  **Job Chain**:
    - `release-payout`: Moves balance from `pending` to `available` in the local DB.
    - `execute-payout` (New): Triggered daily by a Cron job. Scans for wallets with `balance > 0` and `KYC_APPROVED`.

## 3. Ledger Hardening (ACID)
To prevent double payouts or lost funds during reversals:
- Use **Prisma Transactions** for all wallet updates.
- **Append-only Ledger**: Every state change must have a corresponding `LedgerEntry`.
- **Idempotency**: Payouts must have a `payout_id` (external ID) linked to the `LedgerEntry` to prevent duplicate transfers.

## 4. Security: Bank Data Encryption
Bank details will be encrypted at rest using `AES-256-GCM` with a key stored in environment variables.

### Fields to Encrypt:
- `bank_account_number`
- `bank_branch_number`

## 5. Validation Architecture
- **Unit Tests**: Domain logic for `Wallet.withdraw()` and `PayoutService.calculateFees()`.
- **Integration Tests**: `PagarMePayoutAdapter` using mocks for the gateway API.
- **E2E Tests**: Flow from Wallet balance release -> Automatic Payout creation -> Approval gate.
