## Areas Discussed

### 1. Data Modeling & Schemas
- **Options presented:**
  - Create a central `geo` schema vs distribute `City`/`Neighborhood` across `catalog` and `matching`.
- **User selection:** Central `geo` schema.
- **Notes:** Centralizing geographic entities prevents duplication and keeps the architecture clean.

### 2. Catalog Availability Mapping
- **Options presented:**
  - Map availability at the `Category` level vs `Service` level.
- **User selection:** `Category` level.
- **Notes:** Reduces operational complexity. Enabling a category in a city automatically enables its standard services.

### 3. Matching Engine Strategy
- **Options presented:**
  - Keep PostGIS radial fallback vs switch 100% to Array Intersection (`neighborhoodId IN serviceZoneIds`).
- **User selection:** 100% Array Intersection.
- **Notes:** Maximizes performance (<100ms) by using standard Postgres indexes instead of complex spatial queries. GPS `Location` is retained only for routing/ETA, not primary matching.

### 4. Data Seeding
- **Options presented:**
  - Prisma Seed (with static JSON) vs Migration Scripts vs Internal API endpoint.
- **User selection:** Prisma Seed.
- **Notes:** Simple, reproducible in CI/CD, and avoids external API dependencies during deployment.
