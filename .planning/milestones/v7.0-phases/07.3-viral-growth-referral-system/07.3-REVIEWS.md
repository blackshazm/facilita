# Cross-AI Plan Review — Phase 7.3

## Antigravity (Adversarial Review)

**Summary:**
The plan successfully isolates the referral logic within the Hexagonal Architecture, utilizing BullMQ for the D+15 deferred reward and modifying the `Wallet` to handle promotional credits. The logic correctly protects the platform's cash flow by avoiding direct withdrawable payouts. However, there are a few edge cases related to data uniqueness and lifecycle management that must be addressed before execution.

**Strengths:**
- **Financial Safety:** Separating `promoBalance` from the standard withdrawable `balance` is an excellent choice.
- **Robustness:** Using BullMQ delayed jobs for the D+15 reward is resilient to server restarts and handles the time gap perfectly.
- **Hexagonal Boundaries:** The responsibilities are clearly distributed among the Identity, Orders, and Payments modules.

**Concerns:**
- **HIGH:** **Invite Code Collisions.** Generating `inviteCode` as `FIRSTNAME + 3 random digits` has a high risk of collision as the user base grows. If a collision occurs during registration, the Prisma insert will throw a unique constraint error, blocking user registration.
- **MEDIUM:** **Reward Cancellation on Dispute.** The plan specifies checking if the order is still `DONE` after 15 days, but if an order is refunded or disputed *during* those 15 days, it's more efficient to cancel the BullMQ job immediately rather than letting it execute and fail.
- **LOW:** **Frontend Visibility.** The plan doesn't explicitly mention exposing the `promoBalance` or `inviteCode` via the `get-user.usecase.ts` endpoint, meaning the frontend won't have the data to display the referral screen.

**Suggestions:**
- Add a retry loop in `auth.service.ts` for invite code generation (e.g., if collision, append more characters or regenerate).
- Ensure `get-user.usecase.ts` is updated to return `inviteCode`, `referralCount`, and `Wallet.promoBalance`.
- In the disputes module or order refund logic, add an event listener that attempts to remove the `schedule-referral-reward` job from BullMQ if the order status changes from `DONE`.

**Risk Assessment:** **MEDIUM**
The core financial logic is safe, but the high risk of registration failure due to `inviteCode` collisions needs to be patched in the plan.
