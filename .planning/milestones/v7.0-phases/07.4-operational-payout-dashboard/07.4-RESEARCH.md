## Summary

The operational payout dashboard connects the existing backend `PayoutStatus` logic to a new admin interface. The research confirms that the existing stack (NestJS with Prisma on the backend, and Next.js with Tailwind CSS on the frontend) has all necessary tools to implement this safely. 

**Primary recommendation:** Build specific admin use cases in the backend that enforce `UserRole.ADMIN` and automatically call `FinancialAuditService` upon state mutation, rather than directly modifying the payout rows from the client.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| State Transition | API / Backend | Database | NestJS use cases handle the state transition from PENDING_APPROVAL to PROCESSING/CANCELLED and log the action. |
| Role Verification | API / Backend | Frontend Server | Endpoints must be protected by JwtAuthGuard and RolesGuard. |
| UI Rendering | Browser / Client | Frontend Server | Next.js App router renders the dashboard and client-side hooks manage interaction state. |

### Anti-Patterns to Avoid
- **Direct Database Mutation from UI:** Do not expose a generic `PATCH /payouts/:id` endpoint. Use specific semantic endpoints like `/admin/payouts/:id/approve` to ensure the audit log is always captured.

## Common Pitfalls

### Pitfall 1: Missing Audit Logs
**What goes wrong:** An admin approves a payout, but it is not recorded in the `FinancialAuditLog`.
**Why it happens:** The developer calls `payoutRepository.save()` directly without invoking `FinancialAuditService.logAction()`.
**How to avoid:** Inject `FinancialAuditService` into the new admin use cases and enforce its call during the approval/blocking flow.
