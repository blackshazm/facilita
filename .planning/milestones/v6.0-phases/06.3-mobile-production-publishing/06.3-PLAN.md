## Wave 1: Infrastructure & Production Setup

### Task 1.1: Configure EAS Build & Credentials
- **Action**: 
    - Update `apps/provider/eas.json` with `development`, `preview`, and `production` profiles.
    - Add `build.credentials` section for iOS/Android code signing.
- **Acceptance Criteria**:
    - `eas.json` contains signing configuration.
    - `eas build --profile production --dry-run` passes validation.

### Task 1.2: App Store Metadata & Privacy
- **Action**: Create Privacy Manifest (required by Apple) and update `app.json` with data collection disclosures.
- **Acceptance Criteria**:
    - `ios.privacyManifest` present in `app.json`.
    - Permissions (Camera, Location, Notifications) have descriptive usage strings.

## Wave 3: Resilient Push Notifications

### Task 3.1: Backend Notification Engine (Retries & Rate Limits)
- **Action**: 
    - Implement `NotificationModule` with BullMQ retry configuration (exponential backoff).
    - Add rate limiting (Max 10 notifications/user/hour).
- **Acceptance Criteria**:
    - Failed notifications are automatically retried by the worker.
    - Spam prevention blocks excessive notifications.

### Task 3.2: Mobile Push & Token Lifecycle
- **Action**: Implement token registration and periodic refresh (on app foreground).
- **Acceptance Criteria**:
    - Valid token stored in `UserDevice` table.
    - Tokens marked as inactive on `DeviceNotRegistered` error.

---

## Wave 4: Offline Resilience & UI Polish

### Task 4.1: Offline Caching (AsyncStorage)
- **Action**: Persist `activeOrder` and `providerProfile` data.
- **Acceptance Criteria**: Data persists across app restarts without network.

### Task 4.2: Connectivity UX (Retry Flow)
- **Action**: Implement `OfflineBanner` and "Manual Retry" button for failed offline actions.
- **Acceptance Criteria**: User can manually retry a "Confirm Order" action after Signal is restored.
