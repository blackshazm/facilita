# Phase 08.2: Payout Resilience & Automation - Context

**Gathered:** 2026-05-20
**Status:** Ready for planning

<domain>
## Phase Boundary

Automatização da reconciliação de status de repasses a prestadores de serviço (payouts) através da implementação de listeners de webhooks do Pagar.me, garantindo segurança criptográfica e resiliência financeira com estornos automáticos em caso de falha.
</domain>

<decisions>
## Implementation Decisions

### Ciclo de Vida & Resolução do Lote
- **D-01 (Resolução do Lote):** O lote (`PayoutBatch`) rastreia apenas o disparo inicial bem-sucedido para o gateway, sendo marcado como `COMPLETED` após o processador terminar de enfileirar todos os itens. Falhas assíncronas posteriores de repasses individuais notificadas via webhook são tratadas estritamente de forma individual no nível de `Payout` (mudança de status para `FAILED` e execução de estorno via `ReverseFailedPayoutUseCase`), sem alterar o status geral do lote.

### Segurança do Webhook
- **D-02 (Segurança de Assinatura):** Validação híbrida da assinatura do cabeçalho `x-pagarme-signature`. Em ambiente de Produção, a verificação criptográfica estrita via HMAC-SHA256 usando o `PAGARME_WEBHOOK_SECRET` é obrigatória, rejeitando requisições sem assinatura válida com `401 Unauthorized`. Para testes locais e automação de UAT, a validação da assinatura é contornada de forma segura caso a chave de testes do Pagar.me (`PAGARME_SECRET_KEY`) esteja configurada como `sk_test_mock`.

### Resiliência & Tratamento de Erros
- **D-03 (Tratamento de Falhas Bancárias):** Abordagem orientada a eventos desacoplados. Quando o webhook do Pagar.me sinalizar que uma transferência falhou (`transfer.failed`), o endpoint de webhook realiza o estorno do saldo via `ReverseFailedPayoutUseCase`, registra formalmente o incidente no `FinancialAuditLog`, e dispara o evento de domínio NestJS `payout.failed`. Alertas operacionais adicionais são consumidos de forma assíncrona por listeners deste evento.
- **D-04 (Garantias de Idempotência):** O endpoint de processamento do webhook deve ser estritamente idempotente. Antes de aplicar transições de status no banco ou disparar estornos de saldo, o sistema deve verificar se o `Payout` já está em um estado terminal (`PAID` ou `FAILED`). Se estiver, o webhook deve retornar sucesso `200 OK` imediatamente, evitando execuções repetidas.

### a agent's Discretion
- A escolha exata da assinatura criptográfica e estrutura de resposta do controller de webhook é de discrição do agente, desde que respeite os padrões definidos pelo Pagar.me e a interface existente.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `PaymentWebhookController` (`apps/api/src/modules/payments/interface/http/payment.webhook.controller.ts`): Controlador existente que lida com webhooks do Pagar.me, contendo estrutura inicial para captura de pagamentos. Deve ser expandido para aceitar as rotas e eventos de transferências.
- `ReverseFailedPayoutUseCase` (`apps/api/src/modules/payments/application/reverse-failed-payout.usecase.ts`): Use case existente que escuta o evento `payout.failed` e realiza o estorno do saldo da carteira do provedor no ledger.
- `PagarMePayoutAdapter` (`apps/api/src/modules/payments/infrastructure/gateways/pagarme-payout.adapter.ts`): Adapter responsável pela integração com o gateway, contendo suporte a mock de testes com a chave `sk_test_mock`.

### Established Patterns
- **NestJS Event-Emitter**: Usado para despacho desacoplado de eventos de domínio no ecossistema de pagamentos.
- **Mock de Testes Automatizados**: Uso da chave `sk_test_mock` para simular requisições locais estáveis sem bater na API real do Pagar.me.

### Integration Points
- **findByExternalId no PrismaPayoutRepository**: É necessário implementar a porta e o adapter `findByExternalId(externalId: string): Promise<PayoutProps | null>` para buscar o Payout correspondente ao `externalId` recebido no body do webhook do Pagar.me.

</code_context>
