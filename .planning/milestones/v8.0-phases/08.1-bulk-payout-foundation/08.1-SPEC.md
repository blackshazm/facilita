# Phase Spec: 08.1 — Bulk Payout Foundation

## Goal
Establish a scalable and safe foundation for processing provider payouts in bulk, reducing manual administrative effort and ensuring financial consistency between the internal ledger and the Pagar.me gateway.

## Requirements

### 1. Pending Payouts Interface
- **Statement**: Create a dedicated administrative screen for managing pending provider payouts.
- **Current State**: Payouts are viewed individually in the general ledger or order details.
- **Target State**: A new tab "Pagamentos Pendentes" under the Admin/Financial section listing all Ledger entries with status `PENDING_PAYOUT`.
- **Acceptance Criterion**: Admin can view a list of all providers waiting for payment with their respective amounts and bank data status.

### 2. Batch Selection & Execution
- **Statement**: Allow the selection of multiple payout entries to be processed as a single batch.
- **Current State**: Payouts must be triggered one by one.
- **Target State**: Checkboxes for each row, a "Select All" option, and a "Process Selected" button.
- **Acceptance Criterion**: Admin can select up to 100 items and trigger the batch. A confirmation modal must show the total amount and count.

### 3. Real-time Balance Monitoring
- **Statement**: Display the actual gateway balance to prevent over-drafting.
- **Current State**: No visibility of Pagar.me balance in the Admin dashboard.
- **Target State**: A "Gateway Status" widget showing Pagar.me available balance vs. total pending in the internal ledger.
- **Acceptance Criterion**: Dashboard displays a real-time (cached < 1 min) balance fetched via Pagar.me API.

### 4. Idempotent Batch Processing
- **Statement**: Use BullMQ to process batch payouts with mandatory idempotency keys.
- **Current State**: Individual payouts use idempotency but no batch orchestration exists.
- **Target State**: `BatchPayoutService` that enqueues BullMQ jobs. Each job uses the Ledger Entry UUID as the Pagar.me `idempotency_key`.
- **Acceptance Criterion**: Repeating the same batch or job results in no duplicate transfers in Pagar.me.

### 5. Intelligent Batch Interruption
- **Statement**: Stop batch processing if the gateway balance becomes insufficient.
- **Current State**: N/A
- **Target State**: If a transfer fails with `insufficient_funds`, the system marks remaining items in the batch as `FAILED_NO_FUNDS` and halts the queue.
- **Acceptance Criterion**: No further API calls are made after the first balance failure in a batch.

## Boundaries

### In Scope
- Admin UI for selecting pending payouts (web only).
- `BatchPayoutService` and BullMQ worker implementation.
- Pagar.me balance widget in Admin.
- Basic error logging for batch failures.

### Out of Scope
- Automated payout scheduling (Phase 07.1 already handles basic scheduling; this is for manual bulk execution).
- Payout conciliation webhooks (deferred to Phase 08.2).
- Automatic bank account correction UI.

## Acceptance Criteria
- [ ] New "Pagamentos Pendentes" screen exists and loads entries correctly.
- [ ] Admin can select up to 100 items and trigger a batch.
- [ ] BullMQ processes the transfers asynchronously.
- [ ] Gateway balance is visible in the dashboard.
- [ ] Batch stops immediately if balance is insufficient.
- [ ] No double-payouts occur on job retries (Idempotency check).
