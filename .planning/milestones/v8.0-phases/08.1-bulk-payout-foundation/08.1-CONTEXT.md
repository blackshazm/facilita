<decisions>
## Implementation Decisions

### API & Orquestração
- **D-01: Endpoint de Lote**: Criar `POST /admin/payouts/batch` que recebe um array de IDs de Ledger. O backend valida a existência e status de cada item antes de enfileirar.
- **D-02: BullMQ Strategy**: Cada transferência individual será um job no BullMQ. A concorrência será limitada a 2 para evitar rate limits.
- **D-03: Idempotência**: O `idempotency_key` enviado ao Pagar.me será o UUID da entrada correspondente no Ledger.

### Interface & UX
- **D-04: Monitoramento de Progresso**: Utilizar Polling no Frontend para consultar o status do lote via `GET /admin/payouts/batch/:id`.
- **D-05: Notificações**: Implementar Toasts persistentes no Dashboard Admin para informar conclusão ou erro crítico do lote, permitindo navegação livre durante o processamento.
- **D-06: Localização**: Nova aba dedicada dentro de `/admin/payouts`.

### Segurança Financeira
- **D-07: Balance Check**: O sistema deve consultar o saldo disponível no Pagar.me via API antes de iniciar o lote e interromper imediatamente se uma falha de saldo ocorrer durante a execução.

</decisions>
