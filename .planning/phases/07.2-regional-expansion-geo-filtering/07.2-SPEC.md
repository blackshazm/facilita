# Phase 7.2: Regional Expansion & Geo-Filtering — Specification

**Created:** 2026-05-06
**Ambiguity score:** 0.08 (gate: ≤ 0.20)
**Requirements:** 3 locked

## Goal

Enable multi-city operations by implementing a city-based service discovery and provider matching system that uses neighborhood-level "Service Zones".

## Background

Currently, the `MatchingEngine` operates on a simple point-radius basis (1km, 5km, 10km) and does not respect municipal boundaries. The `Catalog` returns all available service categories regardless of the user's location. As the platform scales beyond its initial pilot city, we need to ensure that customers only see services available in their municipality and that providers only receive orders within their designated service areas to maintain logistical efficiency.

## Requirements

1. **City-Aware Catalog**: The service catalog must filter categories and services based on the user's current city.
   - Current: `GetCatalogUseCase` returns all categories and services from the database regardless of user location.
   - Target: `GetCatalogUseCase` accepts a `cityId` and returns only services available in that city (based on a whitelist of active cities).
   - Acceptance: Requesting the catalog with `cityId = 'sao-paulo'` returns services; requesting with an inactive `cityId` returns an empty catalog or a "Coming Soon" state.

2. **Provider Service Zones**: Providers can define their availability by selecting specific neighborhoods/districts within a city.
   - Current: Providers have no concept of "Service Zones"; matching is based solely on their last reported GPS coordinate and a fixed radius.
   - Target: `ProviderProfile` includes a list of `ServiceZone` IDs (neighborhoods). Providers can update this list via the app.
   - Acceptance: A provider's profile in the database correctly stores a list of neighborhood IDs; matching engine uses these IDs instead of simple radius.

3. **Regional Matching Engine**: The matching engine must filter providers by their defined Service Zones and ensure they belong to the same city as the order.
   - Current: `MatchProviderUseCase` uses `findNearbyProviders` with expanding radii (1km, 5km, 10km).
   - Target: `MatchProviderUseCase` first filters providers by `cityId` and then checks if the order's neighborhood is within the provider's `ServiceZones`. Radius matching is deprecated or used only as a secondary sorting factor.
   - Acceptance: An order in "Moema" (São Paulo) only notifies providers who have "Moema" in their Service Zones; providers in "Centro" (São Paulo) are not notified even if they are within 10km.

## Boundaries

**In scope:**
- `City` and `Neighborhood` entities/tables.
- `ServiceZone` management in the Provider Profile.
- City-based filtering in the Catalog API.
- Neighborhood-based matching logic in the `MatchingEngine`.
- Migration of existing "Global" services to specific cities (e.g., São Paulo).

**Out of scope:**
- Custom polygon drawing on maps (Neighborhood list only).
- Inter-city service matching (Strict city limits enforced).
- Dynamic geo-fencing pricing (Standard pricing remains).
- Public transportation route matching.

## Constraints

- **Performance**: Neighborhood matching must use indexed IDs (integer or UUID) to ensure < 100ms matching time for 10,000+ providers.
- **Data Source**: Use a fixed whitelist of cities and their corresponding neighborhoods (e.g., IBGE data for Brazil).

## Acceptance Criteria

- [ ] Catalog API filters services by `cityId` correctly.
- [ ] Providers can select multiple neighborhoods in their profile.
- [ ] `MatchingEngine` only matches providers whose Service Zones include the order's neighborhood.
- [ ] Orders are never matched with providers from a different city.
- [ ] System handles "City Not Supported" state gracefully in the UI.
