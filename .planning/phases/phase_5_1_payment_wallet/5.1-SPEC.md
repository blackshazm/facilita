# Phase 5.1: Payment Escrow & Wallet Module — Specification

**Created:** 2026-05-02
**Ambiguity score:** 0.16 (gate: ≤ 0.20)
**Requirements:** 4 locked

## Goal

Implement a secure Escrow-based payment flow with a double-entry Wallet system for providers, integrated with Pagar.me to support tiered payouts.

## Background

Currently, the `payments` module contains only empty scaffolding. The Prisma schema has a `Payment` model linked to `Order`, but no business logic exists for processing transactions, managing escrow, or tracking provider balances. Orders are matched, but there is no mechanism to hold or release funds based on service completion. This phase establishes the financial core of the platform.

## Requirements

1. **Ledger-based Wallet**: Implement a double-entry ledger system to track provider balances with full auditability.
   - Current: No Wallet or Ledger models exist; no balance tracking for providers.
   - Target: `Wallet` (current balance) and `WalletTransaction` (immutable ledger entries) models added to `payments` schema; balance updates occur exclusively via ledger transactions.
   - Acceptance: Creating a credit transaction (e.g., service payment) increases balance; a debit (e.g., payout) decreases it; `wallet.balance` must always match the sum of its transactions.

2. **Escrow Flow (Pagar.me)**: Integrate Pagar.me Pre-authorization at Match and Capture at Done.
   - Current: Payments are not processed; no connection to Pagar.me API.
   - Target: `OrderMatchedEvent` triggers Pagar.me Authorization; `OrderDoneEvent` triggers Pagar.me Capture; `OrderCanceledEvent` triggers Authorization Voiding.
   - Acceptance: Successfully authorized payment appears in Pagar.me as "Authorized"; after order is "DONE", status in Pagar.me changes to "Paid" and funds are released for splitting.

3. **Tiered Payout Scheduler**: Automated payout scheduling based on provider performance tiers.
   - Current: No payout scheduling or tier-based logic.
   - Target: BullMQ job scheduled at `OrderDoneEvent` with a delay based on the provider's current Tier (Bronze: D+15, Prata: D+7, Ouro: D+2); job triggers the actual transfer via Pagar.me Split API.
   - Acceptance: A payout for a Bronze provider is scheduled for execution 15 days after service completion; Ouro provider payout is scheduled for 2 days.

4. **Marketplace Split**: Automatic fee deduction based on service category.
   - Current: No fee calculation or split logic.
   - Target: Every captured payment is automatically split between the Provider's Wallet and the Marketplace account according to the `% fee` defined in the service's `Category`.
   - Acceptance: A R$ 100 service in a 15% fee category results in R$ 85 credited to the provider's wallet (ledger) and R$ 15 retained by the platform.

## Boundaries

**In scope:**
- `Wallet` and `WalletTransaction` models (Prisma).
- Pagar.me Integration Service (Auth, Capture, Refund, Split).
- PIX and Credit Card payment methods.
- Tier-based delay calculation logic.
- BullMQ workers for asynchronous payout execution.
- Internal Domain Events for financial movements.

**Out of scope:**
- Manual withdrawal requests (all payouts are automated based on tier).
- Generation of fiscal documents (NF-e/NFS-e).
- Support for multiple bank accounts per provider (uses the one from onboarding).
- Advanced financial analytics dashboard for providers.
- Chargeback/Dispute automated resolution (handled manually in Phase 5.2).

## Constraints

- **Architecture**: Must strictly follow the **Modular Hexagonal Evolutivo** pattern (Core/Ports/Adapters).
- **Communication**: Cross-module interaction only via `shared/events` and `EventEmitter2`.
- **Security**: Pagar.me API Keys must be encrypted/managed via Environment Variables.
- **Resilience**: All financial transfers must be idempotent to prevent double-payouts.

## Acceptance Criteria

- [ ] `Wallet` and `WalletTransaction` models implemented and migrated in Prisma.
- [ ] Pagar.me Authorization triggered on `OrderMatchedEvent` with correct amount.
- [ ] Pagar.me Capture triggered on `OrderDoneEvent`.
- [ ] Payout jobs are visible in Redis/BullMQ with the correct `delay` per Provider Tier.
- [ ] Split calculation correctly deducts Category-based % fee before crediting Wallet.
- [ ] Every financial movement has a corresponding `WalletTransaction` entry (Audit Trail).
