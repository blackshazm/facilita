<decisions>
## Implementation Decisions

### Gestão Monetária
- **D-01: Inteiros para Centavos**: Todos os valores financeiros serão armazenados e processados internamente como **inteiros em centavos** (ex: 10000 para R$ 100,00). Isso evita erros de precisão decimal e arredondamento durante cálculos de Split. A conversão para Decimal ocorre apenas na camada de interface/apresentação.

### Arquitetura de Consistência
- **D-02: Consistência Eventual para o Ledger**: A atualização do saldo na `Wallet` (Ledger) será processada de forma assíncrona após a confirmação de captura do pagamento pelo Pagar.me. O fluxo será: Pagar.me -> Webhook -> `PaymentCapturedEvent` -> Ledger Update Worker. Isso garante que a API de pagamentos permaneça resiliente e rápida.

### Dados de Provedor
- **D-03: Enum de Tier no ProviderProfile**: Adicionar o campo `tier` (enum: BRONZE, PRATA, OURO) diretamente no modelo `ProviderProfile`. O valor padrão será `BRONZE`. Esta decisão desbloqueia o agendamento de repasses (D+15, D+7, D+2) sem depender da conclusão total do motor de tierização (Fase 5.2).

### Resiliência e Reconciliação
- **D-04: Idempotência de Webhooks**: O handler de webhooks do Pagar.me deve ser idempotente, utilizando o `externalId` (Pagar.me ID) como chave única para evitar créditos duplicados na carteira em caso de reprocessamento.
- **D-05: Job de Reconciliação Diária**: Implementar um job (BullMQ/Cron) que verifica pagamentos em estado `AUTHORIZED` há mais de 24h sem captura confirmada, disparando alertas ou tentativas de captura manual.

### the agent's Discretion
- Choice of Pagar.me SDK vs direct API calls.
- Internal structure of the `payments` module folders (Ports/Adapters).

</decisions>
