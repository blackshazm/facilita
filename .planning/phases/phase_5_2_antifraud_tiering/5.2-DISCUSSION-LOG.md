# Discussion Log — Phase 5.2: Anti-fraud & Tiering Engine

## 1. Areas Discussed

### Anti-fraud Rules & Tiers (Business Logic)
- **Velocity Check**: Defined as 20 services per 24h.
- **Fees**: Set to 22% (Bronze), 20% (Prata), 18% (Ouro).
- **Tiers**: Bronze (start), Prata (10+ serv, >4.5 rating), Ouro (50+ serv, >4.8 rating).
- **Geofencing**: Confirmed at 500m tolerance with mandatory check-in.

### Backend Validation (Technical)
- **Decision**: Strict physical block on Backend (403 Forbidden) using PostGIS coordinates validation during check-in.
- **Rationale**: Prevent bypass of frontend-only GPS checks.

### Fraud Detection Flow (Technical)
- **Decision**: Asynchronous detection via `order.completed` event listeners.
- **Rationale**: Maintain performance of the main order flow while ensuring auditability.

### Security (Technical)
- **Decision**: Extend `UserRole` enum with `ADMIN` and use NestJS `RolesGuard`.
- **Rationale**: Native integration with existing Identity module.

### Background Jobs (Technical)
- **Decision**: Use BullMQ Repeatable Jobs for daily tier recalculation.
- **Rationale**: Reliability, persistence in Redis, and monitoring capabilities.
