# Phase 7.3: Viral Growth & Referral System - SPEC

## 1. Phase Boundary
This phase implements a self-sustaining referral engine designed to acquire new users and providers organically without draining the platform's cash reserves. It introduces invite codes, deferred promotional credits (D+15), and strict anti-fraud limits (max 200 referrals). 

**Out of Scope:**
- Multi-level marketing (MLM) or tiered referral structures.
- Direct cash payouts for referrals.

## 2. Core Requirements

### GROW-01: Invite Code & Tracking
- **Requirement:** Every user (Customer or Provider) must have a unique, human-readable invite code (e.g., `NOME123`).
- **Context:** The code is generated at account creation. When a new user registers using an invite code, the system links the new user (Referee) to the referrer.
- **Constraint:** Codes must be case-insensitive and unique across the entire platform.

### GROW-02: Deferred Reward Engine (D+15)
- **Requirement:** Both the Referrer and the Referee receive a bonus of **R$ 10,00** *only if* the Referee completes a successful service (`DONE` and `PAID`).
- **Context:** The bonus is not credited immediately upon order completion. It is scheduled to be credited **15 days** after the completion of the Referee's first order. If the Referee never uses the platform, no bonus is generated.
- **Constraint:** The reward is strictly a "Promotional Credit", not withdrawable cash.
  - **For Customers:** It acts as a discount on their next service request.
  - **For Providers:** It acts as a discount/subsidy against the platform's marketplace fee on their future orders (keeping cash inside the ecosystem).

### GROW-03: Hard Limits & Anti-Fraud
- **Requirement:** A strict global limit of **200 successful referrals** per user.
- **Context:** Once a user hits 200 referrals, their code no longer grants rewards unless an Admin manually increases their limit (e.g., for influencer collaborations).
- **Constraint:** The system must detect and block self-referrals by validating `deviceId`, `IP`, and payment methods (a user cannot use a credit card that already belongs to the referrer).

## 3. Acceptance Criteria (Falsifiable)

1. **Code Generation:** Given a new user registers, an invite code is automatically generated and saved to their profile.
2. **Referral Linkage:** Given a user registers with an invite code, the system records the `invitedById`.
3. **Reward Scheduling:** Given a Referee completes their first order, a background job is scheduled for D+15 to credit R$ 10,00 to both the Referrer and Referee.
4. **Reward Expiration/Void:** Given a Referee's first order is disputed or refunded within the 15-day window, the scheduled reward is canceled.
5. **Customer Discount:** Given a Customer has R$ 10,00 in promotional credit, their next service order automatically deducts R$ 10,00 from the total cost.
6. **Provider Fee Discount:** Given a Provider has R$ 10,00 in promotional credit, the platform fee for their next order is reduced by up to R$ 10,00.
7. **Referral Cap:** Given a user has reached 200 successful referrals, any subsequent use of their invite code does not generate new scheduled rewards, and the Referee is notified that the code has expired.
8. **Admin Override:** Given an Admin updates a user's `referralLimit` to 1000, the user can continue receiving rewards up to the new limit.
9. **Sybil Block:** Given a registration uses an invite code from a device with a matching `deviceId` to the Referrer, the linkage is silently ignored or flagged as fraudulent.

## 4. Ambiguity Assessment
- **Clarity:** HIGH. The 15-day deferral, exact amount (R$ 10), and strict cap (200) leave no room for interpretation.
- **Risk:** LOW. By using promotional credits (discounts) instead of cash payouts, the financial risk to the platform is negligible.
- **Testability:** HIGH. The D+15 scheduling and limit enforcement can be easily tested with mock dates and counter manipulation.
