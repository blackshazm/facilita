# Plan — Phase 7.3: Viral Growth & Referral System

## Overview
Implement the referral system with a D+15 delayed reward of R$ 10,00 (Promotional Credit) for both the referrer and referee. This includes tracking invite codes, detecting fraud (Sybil attacks), and automatically applying discounts on future orders or platform fees.

## Wave 2: Invite Code Generation & Registration Tracking
### Tasks
<task read_first="apps/api/src/modules/identity/application/auth.service.ts" acceptance_criteria="auth.service.ts handles invite code generation and linkage.">
<action>
1. Modify user registration logic in `apps/api/src/modules/identity/application/auth.service.ts`:
    - Generate a unique `inviteCode` (e.g., `FIRSTNAME` + 3 random digits, slugified and uppercased) when creating a new `User`.
    - Accept an optional `inviteCode` in the registration payload.
    - If provided:
        - Find the referrer by `inviteCode`.
        - If referrer exists and `referralCount < referralLimit`:
            - Check `UserDevice` to ensure the `deviceId` does not match any device owned by the referrer.
            - If valid, set `invitedById = referrer.id`.
</action>
</task>

## Wave 3: D+15 Reward Trigger & Processor
### Tasks
<task read_first="apps/api/src/modules/orders/application/order.service.ts" acceptance_criteria="order.service.ts dispatches a delayed job when an order completes.">
<action>
1. Modify `apps/api/src/modules/orders/application/order.service.ts`:
    - In the function that marks an order as `DONE` and `PAID`:
        - Check if the `Order.userId` (Customer) has an `invitedById` set.
        - Check if this is the user's FIRST completed order.
        - If yes, dispatch a `schedule-referral-reward` job to BullMQ with a 15-day delay (`15 * 24 * 60 * 60 * 1000` ms). Payload: `{ refereeId: string, referrerId: string, orderId: string }`.
</action>
</task>

<task read_first="apps/api/src/modules/payments/infrastructure/queues/payout.processor.ts" acceptance_criteria="A new processor handles the referral reward credit.">
<action>
1. Create `apps/api/src/modules/payments/infrastructure/queues/referral-reward.processor.ts`:
    - Process `schedule-referral-reward` jobs.
    - Check if the original `orderId` is still `DONE` and not disputed/refunded.
    - Increment `promoBalance` by 1000 (R$ 10,00 in cents) for both `refereeId` and `referrerId` wallets.
    - Create `WalletTransaction` records of type `PROMO_CREDIT` for both.
    - Increment `referralCount` for the `referrer`.
</action>
</task>

## Wave 4: Discount Application
### Tasks
<task read_first="apps/api/src/modules/orders/application/order.service.ts" acceptance_criteria="order.service.ts applies promo discount to the total amount.">
<action>
1. Modify `order.service.ts` or the payment flow:
    - Before creating a new order charge, check the customer's `Wallet.promoBalance`.
    - If `promoBalance > 0`:
        - Deduct up to R$ 10,00 from the `totalAmount` charged to the customer.
        - Decrement the customer's `promoBalance` accordingly.
        - Add a `WalletTransaction` of type `DEBIT` (description: "Desconto Promocional").
</action>
</task>

<task read_first="apps/api/src/modules/payments/application/process-daily-payouts.usecase.ts" acceptance_criteria="Marketplace fee is subsidized by promo balance.">
<action>
1. Modify `process-daily-payouts.usecase.ts` (or the gateway split calculation):
    - When calculating the platform fee (`marketplaceFee`) for a provider's service:
        - Check the provider's `Wallet.promoBalance`.
        - If `promoBalance > 0`, reduce the `marketplaceFee` by up to R$ 10,00, allowing the provider to keep more of the total order value.
        - Decrement the provider's `promoBalance` and record the transaction.
</action>
</task>
