# Research — Phase 7.3: Viral Growth & Referral System

## 1. Current State Analysis
- **User and Provider Models:** Currently, `User` and `ProviderProfile` are separate entities in the `identity` schema. Both can act as referrers or referees. There is currently no `inviteCode` or tracking relationship.
- **Wallet and Transactions:** The `Wallet` model tracks cash balances (in cents). The system handles Escrow and Payouts via `WalletTransaction`. There is currently no distinction for non-withdrawable promotional balances.
- **Order Flow:** `order.service.ts` tracks order status. A check-in flow is implemented, but there is no explicit `completeOrder` use case in the current simplified service. The transition to `DONE` status is likely handled elsewhere or needs to be expanded.
- **Background Jobs:** BullMQ is used in the `payments` module for `ExecutePayoutProcessor`, proving that delayed background jobs are fully supported by the infrastructure.

## 2. Dependency Mapping
- **Database (`schema.prisma`):**
  - Requires adding self-referential relations to `User` for `invitedById`.
  - Requires adding `promoBalance` to `Wallet`.
  - Requires extending `TransactionType` with `PROMO_CREDIT`.
- **Identity Module:**
  - `auth.service.ts` (or the equivalent user creation use case) must be modified to generate slugs and process incoming invite codes.
- **Orders/Payments Module:**
  - Order completion must publish an event or dispatch a BullMQ job.
  - Payment processing must calculate discounts based on `promoBalance` before charging the gateway.

## 3. Technical Approach
1. **Invite Codes:** Generate a random alphanumeric string attached to the user's first name (e.g., `JOAO` + `A8C`). Case-insensitive unique constraint.
2. **D+15 Delay:** Use BullMQ's built-in `delay` option (`{ delay: 15 * 24 * 60 * 60 * 1000 }`) when adding the job to the queue. This is resilient to server restarts.
3. **Discount Calculation:** In the `checkout` or `payment-split` logic, apply `Math.min(totalAmount, promoBalance)` as the discount, updating the `promoBalance` transactionally with the order creation.

## 4. Architectural Risks & Mitigations
- **Risk:** BullMQ delayed jobs filling up memory if millions are scheduled.
  - *Mitigation:* Redis handles delayed jobs efficiently via sorted sets, scaling well up to millions of jobs.
- **Risk:** Race conditions when applying `promoBalance` to two simultaneous orders from the same user.
  - *Mitigation:* Use atomic Prisma updates (`decrement`) or `SELECT ... FOR UPDATE` inside an interactive transaction when deducting `promoBalance`.
- **Risk:** Sybil attacks (user creating fake accounts).
  - *Mitigation:* Check the `UserDevice` model (`deviceId`/`pushToken`) during registration. Reject the referral linkage if it matches the referrer's device.

## 5. Conclusion
The technical foundation is ready. The plan can proceed with the established Hexagonal boundaries, modifying the Identity domain for code tracking and the Payments domain for the reward engine.
