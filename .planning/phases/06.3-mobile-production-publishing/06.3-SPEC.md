# SPEC — Phase 6.3: Mobile Production & Publishing

## Overview
This phase marks the transition of the Provider App from a development baseline to a production-ready application. Key focuses include establishing a professional CI/CD pipeline, implementing push notifications, securing provider onboarding via manual KYC/Selfie validation, and ensuring critical data is available offline.

## Requirements

### 1. CI/CD Pipeline (PRV-01)
- **Statement**: Configure Expo Application Services (EAS) for automated builds and internal distribution.
- **Current State**: Manual local builds only. No EAS configuration.
- **Target State**: `eas.json` configured with `development`, `preview`, and `production` profiles. Builds triggered via CLI and sent to Expo Orbit/TestFlight.
- **Acceptance Criterion**: Successfully generate a `production` build (AAB/IPA) and distribute to an internal testing track.

### 2. Push Notifications (PRV-02)
- **Statement**: Implement end-to-end push notifications for critical order events.
- **Current State**: No notification infrastructure in App or Backend.
- **Target State**: App registers FCM tokens on startup. Backend `NotificationService` (using `expo-server-sdk`) sends notifications for `New Order` and `Chat Message` events.
- **Acceptance Criterion**: Receive a push notification on a physical device after an order is created in the system.

### 3. Manual KYC & Liveness (PRV-03)
- **Statement**: Secure provider onboarding with selfie and document capture for manual admin approval.
- **Current State**: Basic registration screen without document capture logic.
- **Target State**: Onboarding flow includes "Capture Selfie" (Static) and "Capture Document" (Front/Back) steps. Images are uploaded to storage and linked to `KycSubmission` model.
- **Acceptance Criterion**: Provider completes registration with 3 photos; Admin sees these photos in the Backoffice and can approve the account.

### 4. Offline-First Lite (PRV-04)
- **Statement**: Ensure critical order and profile information is available without internet connection.
- **Current State**: App crashes or shows empty screens when offline.
- **Target State**: Current active order and provider profile are persisted locally (AsyncStorage). Offline mode shows a "No Connection" banner and prevents write actions with friendly error messages.
- **Acceptance Criterion**: Disable internet on device; Open app and still see the current active order details.

## Boundaries

### In Scope
- EAS Build configuration (`eas.json`).
- Backend `NotificationModule` in NestJS.
- Manual KYC flow (Selfie + Document photos).
- Basic Offline persistence for Order/Profile.
- TestFlight and Google Play Internal testing tracks.

### Out of Scope
- Automatic KYC validation (3rd party AI integration).
- Active Liveness (gesture detection like blinking).
- Complex offline sync queues (automatic retries).
- Public Store Publishing (Final Production Release).
- Deep-linking from notifications.

## Acceptance Criteria Checklist
- [ ] `eas.json` exists and `eas build --profile production` completes successfully.
- [ ] App prompts for notification permissions and successfully sends token to Backend.
- [ ] Push notification is visible on lock screen when a new order is simulated.
- [ ] Provider registration flow blocked until Selfie and Document photos are captured.
- [ ] Admin Backoffice displays KYC photos for the registered provider.
- [ ] App displays active order data while in Airplane Mode.
- [ ] Attempting to "Start Order" while offline results in a "Sem Conexão" error message instead of a crash.
