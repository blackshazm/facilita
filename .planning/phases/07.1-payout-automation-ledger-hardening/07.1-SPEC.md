# Phase 7.1: Payout Automation & Ledger Hardening — Specification

**Created:** 2026-05-06
**Ambiguity score:** 0.10 (gate: ≤ 0.20)
**Requirements:** 5 locked

## Goal

Automate the financial payout lifecycle by implementing a scheduled transfer engine that moves released wallet balances to providers' bank accounts via Pagar.me V5, with automated failure recovery.

## Background

The platform currently has a `Wallet` system (from Phase 5.1) that handles escrow and released balances. However, the final "Payout" (transferring money from the platform's account to the professional's bank account) is currently manual or not yet automated. This phase introduces the `PayoutService`, bank data management in the Mobile App, and a hardened ledger to ensure no money is lost during transfer failures.

## Requirements

1. **Automated Payout Scheduler**: A background engine to trigger transfers.
   - Current: No automated mechanism to trigger bank transfers; released balance stays in internal wallet.
   - Target: `PayoutService` runs daily, identifying "Released" balances that meet tiering rules (D+15, D+7, D+2) and triggering Pagar.me Payouts.
   - Acceptance: A released balance of R$ 100,00 is automatically queued for payout according to the provider's schedule without manual trigger.

2. **Bank Account Management**: Interface for providers to register accounts.
   - Current: Providers cannot register bank accounts in the app.
   - Target: New "Dados Bancários" screen in the Provider App capturing Bank, Agency, Account, and Type, validated against the user's CPF/CNPJ.
   - Acceptance: Provider can save bank details; system rejects if the CPF/CNPJ does not match the registered Identity.

3. **Automated Reversal (Estorno)**: Self-healing for failed transfers.
   - Current: No automated handling for rejected bank transfers.
   - Target: If Pagar.me returns a failure (e.g., "invalid account"), the system automatically restores the balance to the provider's "Saldo Disponível" in the internal wallet.
   - Acceptance: A failed payout status from the gateway triggers a `Ledger` entry of type `REVERSAL`, and the provider's wallet balance increases by the failed amount.

4. **Failure Notifications**: Transparency for the provider.
   - Current: No notifications for financial status changes beyond order completion.
   - Target: Trigger a Push Notification/In-app Alert when a payout fails and is reversed.
   - Acceptance: Simulated payout failure results in a Push message: "Falha no Payout: O valor de R$ XXX voltou para sua Wallet."

5. **High-Value Authorization Gate**: Manual oversight for large sums.
   - Current: No differentiation between transaction values.
   - Target: Payouts with a total value > R$ 2.000,00 are set to `PENDING_APPROVAL` status and require an admin click in the Backoffice.
   - Acceptance: A payout of R$ 500,00 proceeds automatically; a payout of R$ 2.500,00 stays in `PENDING` until approved by an admin.

## Boundaries

**In scope:**
- `PayoutService` (NestJS) for scheduling and gateway integration.
- Bank account CRUD in the Provider App (Expo).
- Reversal logic in the `Wallet`/`Ledger` module.
- "Payouts Falhos" report in the Admin Dashboard.
- Notification trigger on failure.

**Out of scope:**
- Manual "Withdraw" button (user chose fully automatic).
- Regional Multi-city matching (this is Phase 7.2).
- Referral rewards implementation (this is Phase 7.3).

## Constraints

- Must use **Pagar.me V5 Recipients API**.
- Transaction fees must be logged in a separate `Fees` column in the ledger for financial reconciliation.
- Payouts must only occur for users with `KYC_STATUS = APPROVED`.

## Acceptance Criteria

- [ ] `PayoutService` identifies and processes released balances automatically.
- [ ] Bank data captured in the app is successfully synced to Pagar.me Recipients.
- [ ] Failed transfers result in automatic balance restoration (Estorno) in the internal wallet.
- [ ] Providers receive push notifications upon payout failure.
- [ ] Payouts > R$ 2.000,00 correctly pause for Admin authorization.
- [ ] Ledger remains balanced (Sum of all entries matches Wallet balance) after reversals.
